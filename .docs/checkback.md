Да, это можно сделать.
И тут тебе нужен не “определить зарегистрирован ли он”, а **отличить первого визитёра от уже знакомого браузера**.

Это две разные задачи.

## Что ты хочешь по факту

Ты хочешь 3 состояния:

1. **Совсем новый браузер**
   Показываем жёсткую стену логина. Никакого сайта сзади.

2. **Уже знакомый браузер, но сессия слетела**
   Не показываем “большую фигу”, а пускаем в обычный интерфейс с мягким догоном логина, либо открываем логин без ощущения, что он чужой.

3. **Явный logout**
   Стираем метку “свой браузер”, и в следующий раз снова будет жёсткая стена.

---

## Самая важная мысль

Это **не защита от жуликов как таковая**.
Это защита UX-потока.

Потому что любой жулик, если зайдёт с браузера, где уже есть твоя метка, тоже будет считаться “знакомым браузером”.
Так что:

* **безопасность** должна держаться на нормальной серверной авторизации
* а эта метка — только про **режим входа**

То есть она не должна давать доступ к данным сама по себе.

---

## Нормальная схема

Делается так:

### 1. В localStorage или cookie храним флаг

Например:

```js
localStorage.setItem('teftelear_known_device', '1');
```

Ставим его:

* после успешного логина
* можно после успешной регистрации, если она есть

Удаляем его:

* при logout

---

### 2. На старте приложения читаем этот флаг

Например:

```js
const isKnownDevice = localStorage.getItem('teftelear_known_device') === '1';
```

---

### 3. Дальше проверяем сессию

Как у тебя уже есть `checkAuth()`.

И потом решаем, что рендерить:

* **есть user** → пускаем
* **нет user, но known_device = true** → это свой, просто разлогинен
* **нет user и known_device = false** → жёсткая стена логина

---

## По-простому логика такая

```js
if (!authChecked) return <SplashScreen />;

if (user) return <AppLayout />;

if (isKnownDevice) return <SoftGuestLayout />; // знакомый, но без сессии

return <HardLoginWall />; // совсем новый
```

---

## Но есть важный момент

Ты написал:

> Если он выходит логаутом, то мы уничтожаем куки или метку в бд браузера, которая говорит, что он свой.

Вот это правильно.

То есть:

* **случайный отвал токена / сессии** → known flag оставляем
* **осознанный logout** → known flag удаляем

Тогда поведение будет именно таким, как ты хочешь.

---

## Где хранить

Лучше всего для этого подходит:

### `localStorage`

Плюсы:

* просто
* живёт между перезапусками браузера
* легко удалить при logout

Минусы:

* если очистят storage — браузер снова станет “новым”

Но это в твоём кейсе нормально.

---

## Почему не “метка в БД браузера”

Если ты имеешь в виду IndexedDB — можно, но это уже лишнее.
Для такой задачи `localStorage` хватает за глаза.

---

## Почему не серверная БД

Потому что тебе надо помнить **не пользователя**, а **конкретный браузер на конкретной машине**.

Если хранить это на сервере, там придётся городить:

* device id
* browser fingerprint
* token remember device
* срок жизни
* инвалидation

Это уже тяжёлая история, и она больше про security/device management.

Для UX-задачи проще локальная метка.

---

## Как назвать состояние

Я бы не называл это “свой/чужой” в бизнес-логике.
Лучше что-то нейтральное:

* `knownBrowser`
* `hasVisitedBefore`
* `trustedClient`
* `returningVisitor`

Например:

```js
const KNOWN_BROWSER_KEY = 'teftelear_known_browser';
```

## Практическая схема для zustand

### auth store

```js
import { create } from 'zustand';

const KNOWN_BROWSER_KEY = 'teftelear_known_browser';

export const useAuthStore = create((set, get) => ({
  user: null,
  isChecked: false,
  isKnownBrowser: localStorage.getItem(KNOWN_BROWSER_KEY) === '1',

  setKnownBrowser: (value) => {
    if (value) {
      localStorage.setItem(KNOWN_BROWSER_KEY, '1');
    } else {
      localStorage.removeItem(KNOWN_BROWSER_KEY);
    }

    set({ isKnownBrowser: value });
  },

  setUser: (user) => set({ user }),

  checkAuth: async () => {
    try {
      const user = await apiGetMe();
      set({ user, isChecked: true });
    } catch (e) {
      set({ user: null, isChecked: true });
    }
  },

  login: async (payload) => {
    const user = await apiLogin(payload);
    get().setKnownBrowser(true);
    set({ user });
  },

  logout: async () => {
    try {
      await apiLogout();
    } finally {
      get().setKnownBrowser(false);
      set({ user: null });
    }
  },
}));
```

## И в корневом роуте

```jsx
const user = useAuthStore((s) => s.user);
const isChecked = useAuthStore((s) => s.isChecked);
const isKnownBrowser = useAuthStore((s) => s.isKnownBrowser);

if (!isChecked) {
  return <LoadingScreen />;
}

if (user) {
  return <AppRouter />;
}

if (!isKnownBrowser) {
  return <HardLoginWall />;
}

return <GuestShellWithLoginModal />;
```

## Как это будет ощущаться

### Новый чел

* зашёл
* сразу уткнулся в стену логина
* ничего не видит

### Старый чел, у которого токен сдох

* зашёл
* видит нормальный каркас/облегчённую версию/экран входа без ощущения “ты чужой”
* логинится и работает дальше

### Нажал Logout

* мы удалили серверную сессию
* удалили localStorage-флаг
* теперь он снова новый для этого браузера

---

## Но про “не пустить жуликов”

Вот тут важно не переоценить эту схему.

Она **не мешает жулику**:

* открыть сайт в браузере, где уже есть твой флаг
* увидеть некую “мягкую” версию интерфейса

Поэтому для незалогиненного состояния всё равно нельзя:

* отдавать приватные данные
* показывать реальные ивенты
* раскрывать внутренние маршруты с данными
* грузить защищённый API без auth

То есть “мягкий режим” должен быть только визуально мягким, но не дырявым.

## Итого

Да, твоя идея рабочая.
Реализуется через **локальную метку знакомого браузера**, которую:

* ставим после успешного логина
* не удаляем при случайном отвале сессии
* удаляем при logout

Но считать это защитой от жуликов нельзя — это **UX-фильтр**, а не security-барьер.

Если хочешь, я могу сразу накидать тебе готовую структуру:
**`AuthGate.jsx + zustand store + login/logout flow`** под твой текущий фронт.
