# Tasker — модуль задач и отчётности

> Контекст для быстрого старта новой сессии с ИИ.
> Проектировался в одной сессии 20 июля 2026, следом за Contactor.
> Обновляй по мере реализации.

---

## Идеология

Не todo-лист. **Журнал задач с отчётностью и тайм-трекингом**, где ты то ставишь задачи, то сам исполняешь. Ключевые боли, под которые спроектирован модуль:

- Приходится трекать не только свои дела, но и **задачи коллег** — ставить самому, следить за исполнением, писать отчёт за них.
- Постоянно всплывают **шаблонные проблемы**, унаследованные от прошлых разработчиков (~30% блокеров — одно и то же).
- В реальности у задачи **нет единого временного интервала** — начал, отвлекли на саппорт, вернулся на следующий день. Обычные Gantt-таймлайны с одной полоской это не отражают.
- В Todoist выполненные задачи **пропадают из виду** — теряется история того, что вообще происходило.

Архитектурно Tasker не вводит новых базовых механизмов — он **потребляет уже существующие сущности** (`sys_timer_entries`, `prj_links`, паттерн сателлитов, lifecycle-словарь) как четвёртый/пятый участник.

## Схема

```sql
tsk_tasks
  id                CHAR(26)
  title             VARCHAR         -- Title
  description       TEXT            -- Task — что нужно сделать, markdown
  result            TEXT NULL       -- Result — итог по завершении, НЕ обязателен
  assignee_contact_id  CHAR(26) NULL   -- FK → cnt_contacts. NULL = сам исполняю
  priority_id       INT             -- lifecycle 11-15 (зарезервировано заранее)
  status_id         INT             -- lifecycle 20-24 (on_hold = de facto blocked)
  due_at            DATE NULL
  eventor_event_id  CHAR(26) NULL   -- satellite: задача родилась из события
  parent_task_id    CHAR(26) NULL   -- подзадача / чеклист-пункт
  tracked_seconds   INT DEFAULT 0   -- кэш суммы sys_timer_entries, как part_cost в Exploiter
  sort_order
  created_at, closed_at

tsk_log                              -- по образу cnt_log
  id
  task_id           CHAR(26)
  kind              ENUM('note','status_change','report','blocker','clarification')
  content           TEXT            -- markdown
  blocker_id        CHAR(26) NULL   -- FK → tsk_blockers, только для kind='blocker'
  timer_entry_id    CHAR(26) NULL   -- satellite → sys_timer_entries, отчёт по конкретной сессии
  occurred_at

tsk_blockers                        -- каталог известных/повторяющихся проблем
  id
  title             VARCHAR         -- "Легаси-скрипт миграции БД падает"
  description       TEXT
  occurrence_count  INT             -- денормализация, инкремент при каждой линковке
  created_at
```

### Переиспользуемые сущности (без изменения их схемы)

```sql
sys_timer_entries      -- уже спроектирован в Exploiter, Tasker — второй потребитель
  id
  source_module   ENUM('exploiter','tasker', ...)
  source_id       CHAR(26)          -- → tsk_tasks.id
  started_at      DATETIME
  ended_at        DATETIME NULL     -- NULL = сессия сейчас тикает
  sort_order

prj_links               -- Projector, entity_type='task' был предусмотрен заранее
  project_id      CHAR(26)
  entity_type      ENUM('event','transaction','stuff_item','task')
  entity_id        CHAR(26)         -- → tsk_tasks.id
  role             VARCHAR(50) NULL
```

### Изменение существующих таблиц

`cnt_log` (Contactor) получает четвёртый сателлит — было eventor/stuffer/exploiter, добавляется:

```sql
ALTER TABLE cnt_log ADD COLUMN tasker_task_id CHAR(26) NULL;
```

Так в ленте контакта видно "поставил задачу X" автоматически, без дублирования данных.

## Ключевые архитектурные решения

### Глобальный play/stop — один таймер на всю систему

Правило живёт не в Tasker, а **поверх `sys_timer_entries` целиком**: при старте новой сессии бэк принудительно закрывает (`ended_at = now()`) любую другую открытую запись, **независимо от `source_module`**. Запустил таймер на задаче — остановился таймер на вещи в Exploiter, и наоборот. Один фокус внимания на систему.

### Множественные сессии вместо единого интервала

Ключевая боль, ради которой Tasker и затевался: у задачи нет `started_at`/`due_at` как диапазона для Gantt. Вместо этого — **N записей `sys_timer_entries`** на одну задачу. Начал в 9:00, отвлекли в 10:15, вернулся в 14:00, закрыл в 15:30 — три сессии. На таймлайне это рендерится сегментами с разрывами в одной строке, а не одной полоской.

При остановке сессии — модалка "что делал" (тот же MDXEditor, что и везде) → создаёт `tsk_log` с `kind='report'` и `timer_entry_id`, привязанную к конкретному отрезку. Лог получается **гранулярным по сессиям**, а не "весь день работал над задачей".

### Триада Title / Task / Result

- `title` — короткое имя. Для мелких задач ("Поменять лампу в светильнике бухгалтерии") этого самодостаточно, отдельного лога не требуется.
- `description` (Task) — вход, что нужно сделать.
- `tsk_log` — процесс, гранулярная история по сессиям/статусам/блокерам.
- `result` — сводка на выходе. **Не обязателен** — бэк не блокирует переход в `done` без него. Обязателен по смыслу только для задач, где название само не объясняет что сделано.

### Каталог блокеров вместо свободного текста

Когда всплывает проблема — либо создаёшь новый `tsk_blocker`, либо линкуешь на существующий из каталога. Даёт бесплатную аналитику "какая проблема мешает чаще всего" без ручного тегирования, и покрывает тот самый кейс с 30% шаблонных легаси-косяков.

### Assignee через Contactor, не через users

Коллега не обязан быть юзером системы — он `cnt_contact`. `assignee_contact_id = NULL` значит "исполняю сам". Симметрично: Contactor видит задачу в логе контакта через сателлит `tasker_task_id`.

### Подзадачи / чеклист — одна таблица, разное поведение по UI

`parent_task_id` есть с самого MVP. Если у дочерней записи нет своего `assignee`/`due_at` — это лёгкий чеклист-пункт, просто `title` + `status_id`, без собственного `tsk_log` (избыточно на мелочи). Если есть — полноценная подзадача со своей историей. Технически одна таблица, разница только в UI-паттерне (чекбокс-строка vs полноценная карточка).

### `on_hold` = blocked, не плодим статус

Workflow остаётся `planned / in_progress / done / on_hold / canceled`. Блокер — факт в `tsk_log`, не отдельный статус. Осознанное решение против разрастания сущностей.

### Направления/проекты — через Projector, не новая сущность

"IT-поддержка юзеров", "Хозяйство офиса" — обычные `prj_projects` со `status: active`, без `goal_amount` (он nullable, бюджет не обязателен). Схема `prj_links` уже предусматривала `entity_type: 'task'` заранее.

## UI / UX

### Layout

Сайдбар слева (по образу `SectionsSidenav` Ивентора) + контент справа (по образу табличного вида Эксплойтера):

```
сайдбар (180-220px)          |  основной контент
──────────────────────────────|──────────────────────────
Все задачи                    |  таблица (десктоп) /
Без проекта          [счётчик]|  карточки (мобилка)
──────────────────────────────|
Проекты (цветная точка +      |
счётчик каждый)                |
```

### Таблица (десктоп) / карточки (мобилка)

Колонки: точка приоритета → название → исполнитель (аватар/инициалы, "я" акцентным цветом) → срок (`text-danger` при просрочке) → приоритет. Заблокированные (`on_hold`) — левая цветная полоса-акцент (`border-left`, `border-radius: 0` по правилу односторонних бордеров). Выполненные — приглушены, зачёркнуты, чекмарк вместо точки.

### Быстрые фильтры

- **Статус** — чипы-тоглы: Все / Мои / Делегировано / Заблокировано.
- **Исполнитель** — отдельный ряд аватарок-чипов (я + контакты с активными задачами), мультивыбор.
- **Проект** — из сайдбара.

Все фильтры комбинируются через AND.

### Не прятать выполненные (анти-Todoist)

Вместо скрытия — **топим вниз** в том же списке: сортировка "активные сверху (по due_at/приоритету), done/canceled снизу по closed_at desc". История всегда доступна прокруткой, не теряется.

Пагинация — infinite scroll (курсор по `updated_at`, страница ~30). Без номерного пажинатора — список это лента, не каталог.

### Два уровня лога

1. **Лог одной задачи** — модалка/страница (аналог ReadModal Ивентора): `tsk_log` хронологической лентой — статус менялся → отчёт по сессии → блокер → уточнение.
2. **Глобальная лента активности** — отдельный вид, буквально `FeedView` как в Stuffer, только источник `tsk_log` across all tasks. Отвечает на "что вообще происходило по работе за неделю" без захода в каждую задачу поштучно.

### Таймлайн-вид (сегментированный, не Gantt)

Строка = задача, ось X = время. Полоска состоит из **нескольких сегментов** (по числу `sys_timer_entries`), с разрывами между ними — визуально видно прерывания. Слева на карточке/строке — кнопка Play/Stop, запускающая глобальный таймер.

## На горизонте

- **Вложения к сессиям/логу** — фото из отпуска и подобное. Естественное расширение `tsk_log` (новый `kind='photo'` или attachment-поле), по аналогии с тем, как Booker хранит `content` по типу блока. Не проектируем раньше, чем появится черновик функции.
- **Booker-линковка** — `booker_block_id` на задаче отложен до релиза Booker, по тому же принципу что в Exploiter.
- Полноценный Gantt с редактируемым диапазоном **осознанно отклонён** — не отражает реальность прерывистой работы, сегментированный таймлайн точнее.

## Открытые вопросы (не решены в этой сессии)

- Обязательность `result` для конкретных типов задач (кроме "self-explanatory по title") — пока не формализовано, оставлено на усмотрение юзера без валидации на бэке.
- UI переключения вида: таблица/карточки/таймлайн — единый тумблер в тулбаре или раздельные роуты (`/tasker/table`, `/tasker/timeline`)?
- Массовые операции (batch status change, batch delete) — не обсуждались.
